# CLAUDE.md — Meteo a confronto

PWA (frontend statico + piccolo server Python con SQLite) che confronta le previsioni dei modelli **ICON-2I** (ItaliaMeteo-ARPAE, 2,2 km, solo area italiana, ~87 h) e **ICON-EU** (DWD, 7 km, Europa, ~135 h) per una **località fissa: Faenza** (costante `LOCATION` in `js/app.js`; non c'è ricerca né geolocalizzazione).

## Vincoli di progetto

- **Le fonti esterne le interroga solo il server**, mai il browser: i job in `server/jobs.py`, lanciati da **cron** (`deploy/crontab`), le scaricano in un database **SQLite**; `server/api.py` le serve al frontend come API JSON (`api/forecast`, `api/station`, `api/normals`, `api/status`), in sola lettura, senza toccare le fonti. Server Linux con **nginx** come reverse proxy (`deploy/nginx-meteo.conf`: file statici + `/api/` verso `127.0.0.1:8085`) e l'API come servizio systemd (`deploy/meteo-api.service`). Nessuna API key, **nessun login**.
- **Server: solo libreria standard di Python (≥ 3.9)** — `sqlite3`, `urllib`, `http.server`, `zoneinfo`, `fcntl`; niente `pip install`. **Unica eccezione: numpy e Pillow, installati con `apt` (`python3-numpy`, `python3-pil`), solo per il job del radar** (nowcasting): importarle solo lì, così API, centralina e previsioni funzionano anche senza. Il codice deve andare sia con numpy 1.24 / Pillow 9.4 (Debian 12) sia con numpy 2.x / Pillow 11 (Debian 13). Commenti in italiano come nel frontend.
- **Frontend: nessun build step e nessuna dipendenza npm** a runtime. Il codice gira così com'è nel browser.
- **Preferenze solo nel browser** tramite `localStorage` (vedi `js/storage.js`), insieme a una copia delle previsioni per l'uso offline. Ogni accesso è in `try/catch`: l'app deve funzionare anche se lo storage è bloccato. Il server non conserva nulla degli utenti.
- **Interfaccia in italiano**, commenti nel codice in italiano.
- Percorsi **relativi** (`./`, `js/…`, `api/…`) così l'app funziona anche in una sottocartella (variante commentata in `deploy/nginx-meteo.conf`).

## Avvio in locale

```bash
python3 -m server.jobs all        # popola data/meteo.db (METEO_DB per cambiare percorso)
python3 -m server.api --static    # API + file statici su http://127.0.0.1:8085
python3 -m unittest discover -s tests
```

In locale i job si rilanciano a mano (`python3 -m server.jobs station|forecast|normals [--force]`). `data/` è in `.gitignore`.

Il service worker richiede `http://localhost` o HTTPS (non funziona da `file://`).

## Fonti dati (tutte senza chiave, interrogate solo dal server)

- Previsioni: `https://api.open-meteo.com/v1/forecast?models=italia_meteo_arpae_icon_2i,icon_eu&timezone=auto…`
  Le variabili arrivano con suffisso del modello, es. `temperature_2m_icon_eu`; `server/sources.py` le normalizza in `hourly.models.{i2i,eu}.{variabile}`.
- Metadati run: `https://api.open-meteo.com/data/{metaId}/static/meta.json` — attenzione: per ICON-EU il dataset è `dwd_icon_eu`, non `icon_eu` (campo `meta` in `MODELS` di `sources.py`). Questi metadati sono affidabili e guidano i download (vedi sotto).
- **Modelli di supporto** (`SUPPORT_MODELS` in `sources.py` e `api.js`): **ICON-D2** (`icon_d2`, metadati `dwd_icon_d2`, DWD 2,2 km, dominio fino a 43,18°N, ~48 h, run ogni 3 h) e **AROME HD** (`meteofrance_arome_france_hd`, Météo-France 1,3 km, dominio fino a 16°E, ~48 h, run ogni 3 h), scaricati nella stessa richiesta dei due modelli principali (`SUPPORT_VARS`: pioggia, temperatura, codice; ad `api/forecast` arriva solo `hourly.models.{d2,arome}.precipitation`, il resto serve all'archivio della verifica). Non sono colonne né preferenze: votano nel verdetto dei tragitti (`bikeWindow()`) dove coprono l'intervallo, compaiono nel suo dettaglio e nella pagina Verifica (righe solo se c'è la loro previsione). Colori `--d2` (viola) / `--arome` (magenta), `.dot-d2` / `.dot-arome`.
- Ensemble (probabilità di pioggia): `https://ensemble-api.open-meteo.com/v1/ensemble?models=icon_eu_eps,icon_d2_eps,ecmwf_ifs025…` (`ENSEMBLE_MODELS` in `sources.py`): ICON-EU-EPS 40 scenari ~5 giorni (orario fino a ~48 h, poi ogni 3 ore), ICON-D2-EPS 20 scenari a 2,2 km ~48 h, **ECMWF ENS** 51 scenari 6 giorni, dati **ogni 3 ore** (chiavi con suffisso `ecmwf_ifs025_ensemble`, diverso dall'id: campo `suffix`). **Dati ogni 3 ore**: Open-Meteo divide la pioggia delle 3 ore in parti uguali (stesso valore nelle tre ore, blocchi che finiscono alle ore UTC multiple di 3); `blockStart()` in `app.js` / `coarse_block()` in `verify.py` riconoscono il blocco (tutti gli scenari uguali nelle tre ore) e lì uno scenario è bagnato se il **totale del blocco** ≥ 0,2 mm (diviso in tre servirebbero 0,6 mm in un'ora). Servite in `data.ensemble` come `{ time, groups: [{ model, members }], fetchedAt }`. **I metadati degli ensemble** (`ensemble-api.open-meteo.com/data/dwd_icon_eu_eps/…`) restano fermi per giorni: non usarli per capire se c'è un run nuovo.
- Centralina (dati misurati): `https://www.meteofaenza.it/dati/today/data.js`, Osservatorio "E. Torricelli", aggiornata ~ogni minuto. È un file JavaScript di variabili stringa (`var temperature = '17.2';`: `temperature`, `humidity`, `pressure`, `windSpeed` km/h, `windDirection` °, `rainfall` mm oggi, `dewPoint`, `temperatureMin/Max` + orari, `windSpeedMax` + orario, `currentTimeMillis` = istante della misura): lo scarica il server (`?t=` anti-cache) e `parse_station()` ne estrae i valori con una regex, **senza eseguirlo** (il browser non lo carica più). **I valori del giorno della centralina (`rainfall`, minime/massime, raffica) ripartono a mezzanotte dell'ora solare, cioè alle 01:00 con l'ora legale** (`STATION_DAY_TZ` / `station_day_ok()` in `server/verify.py`): `api.compose_station()` li ricalcola da mezzanotte locale con le letture salvate (`verify.local_day()`: pioggia come somma dei passi `rain_step()`, minime/massime tra letture e valore della centralina se già di oggi; prima dell'azzeramento niente raffica massima, totali del mese/anno corretti al cambio di mese/anno) e restituisce `rainLog` con gli stessi mm da mezzanotte, così app e plugin SwiftBar mostrano sempre i valori del giorno locale. Se il formato cambia, il parsing fallisce (errore nel registro) e resta l'ultima misura salvata.
- **Medie del periodo** (climatologia): `https://archive-api.open-meteo.com/v1/archive?…&models=era5_land&start_date=1991-01-01&end_date=2020-12-31&daily=temperature_2m_max,temperature_2m_min` (`fetch_normals()` / `NORMALS` in `sources.py`): per ogni giorno dell'anno (`day_of_year("MM-DD")` / `dayOfYear()` nel frontend, anno bisestile di riferimento, 366 valori) media dei 30 anni su una finestra circolare di ±7 giorni pesata con i conteggi. Il server le scarica solo se mancano o hanno più di un anno (`NORMALS_MAX_AGE_S`, job giornaliero). ## Layout e responsive

- **Desktop (≥ 1200 px): due colonne 25% / 75%** (`#forecast.layout` grid `1fr 3fr`, `--page-w` 1920 px). Sinistra `.col-side`: centralina (`#now`) e card dei giorni (`#daily`). Destra `.col-main`: andamento orario (grafico) e dettaglio orario. Sotto i 1200 px una sola colonna (prima `.col-side`, poi `.col-main`). Il **piè di pagina** su desktop è in fondo alla colonna sinistra: `placeFooter()` in `app.js` sposta `.footer` dentro `.col-side` con `matchMedia('(min-width: 1200px)')` (stessa soglia del CSS) e lo rimette dopo `<main>` sotto i 1200 px.
- **La colonna sinistra ha sempre l'impaginazione "mobile"**: `.col-side` è un container (`container: side / inline-size`) e le regole compatte di centralina e giorni sono in `@container side (max-width: 560px)` / `(max-width: 720px)`, non in `@media`. Così valgono sul telefono (colonna = schermo) e nella colonna stretta del desktop. In `@media (max-width: 560px)` restano solo intestazione, padding delle card fuori dalla colonna sinistra e tabella oraria.
- Le soglie JS che riguardano i giorni usano la larghezza della colonna, non dello schermo (`fitBikes()`: `#daily.clientWidth` ≤ 560 / ≤ 720). Non usare `matchMedia` per questi elementi.
- Container anonimi annidati (`.obs-card`, `.slots`): le `@container` senza nome trovano il più vicino; quelle della colonna usano il nome `side`.

## Note di dominio

- Non mettere nei box dei modelli variabili assenti in uno dei due, altrimenti il confronto è sbilanciato. Verificare la disponibilità con una chiamata di prova prima di aggiungerne.
- **Dati comuni** (`COMMON_HOURLY` / `COMMON_DAILY` in `api.js`): salvati direttamente in `hourly.<var>` / `daily.<var>`, fuori da `models`, e mostrati fuori dai box dei modelli.

- "Dettaglio orario" è collassabile e **chiuso di default** (`settings.hourlyOpen`, ricordato nel localStorage). Da chiuso la tabella non viene costruita: `renderHourlyTable()` la genera solo quando la sezione è aperta.
- **Tabella oraria** (`renderHourlyTable()`): `table-layout: fixed`, colonna dell'ora a larghezza fissa (`.col-hour`, 56 px; 26 px su mobile) e tutte le altre di uguale larghezza. Intestazione su due righe **senza `rowspan`**, così tutte le etichette sono sulla stessa linea: prima riga etichetta (`.h-label`) con sotto l'unità di misura (`.h-unit`, minuscola, più piccola e chiara; riga vuota se non c'è); seconda riga una cella `.mk` per colonna di modello con una barretta del colore del modello (`::after`, `currentColor` da `.mk.c-i2i` / `.mk.c-eu`) e sopra il nome "2I"/"EU" (`.mk-name`), nascosto su mobile. La cella della probabilità è `td.prob` (non `.pop-cell`: quella delle righe dei giorni è un flex e rompe la cella). Su mobile (≤560 px) deve stare in 390 px senza scorrere: l'ora è mostrata come "07" (`.mm` nascosto) e il simbolo % nelle celle è nascosto. Aggiungendo colonne, ricontrollare `scrollWidth` di `.table-wrap`.
- Oltre l'orizzonte di un modello i valori sono `null`: il rendering deve sempre gestire `null` (mostrare "—" o "oltre l'orizzonte del modello").
- Fuori dal dominio ICON-2I (bbox in `MODELS`) tutti i valori 2I sono `null`: viene mostrato un avviso.
- Gli orari dell'API sono già nell'ora locale della località (stringhe `YYYY-MM-DDTHH:00`): non convertirli con `Date` locale del browser; usare `parts()` e `localNowIso(utcOffset)` di `weather.js`.
- Gli istanti assoluti (ora di download `fetchedAt`, run dei modelli) vanno sempre mostrati nell'**ora locale della località**, mai in quella del dispositivo né in UTC: usare `localDateTime(ms, data.timezone, data.utcOffset)` di `weather.js`.
- **Aggiornamento sul server** (`server/jobs.py`, frequenze in `deploy/crontab` e `server/config.py`):
  - **Centralina** ogni 10 minuti (`*/10`, `sleep 20` perché il file è pubblicato qualche secondo dopo lo scoccare): una riga per misura in `station_readings` (`INSERT OR IGNORE` sull'istante della misura).
  - **Previsioni**: job ogni 15 minuti (minuti 2, 17, 32, 47). Legge sempre i metadati di ICON-2I, ICON-EU, ICON-D2 e AROME (pochi byte; se un modello non risponde si tengono i precedenti) e scarica le previsioni solo se un run è diventato disponibile dopo l'ultimo download, se hanno più di `FORECAST_MAX_AGE_S` (6 h) o con `--force`. **Ensemble** a intervallo fisso, ogni `ENSEMBLE_EVERY_S` (3 h, la frequenza di ICON-D2-EPS). Risultato tipico: ~20 download di previsioni (i run dei quattro modelli escono in momenti diversi) e 8 di ensemble al giorno, per tutti gli utenti.
  - **Medie del periodo**: controllo giornaliero, download solo se mancano o hanno più di un anno.
  - **Fiumi**: job ogni 15 minuti (minuti 7, 22, 37, 52): 1 richiesta per le soglie + 1 per stazione; `INSERT OR IGNORE` sull'istante.
  - **Radar**: job ogni 5 minuti (`*/5`, `sleep 10`: finisce prima della lettura dell'app a +45 s), scarica le immagini nuove (fino alle ultime 4, per colmare un buco), ~225 MB al giorno; ritagli e immagini tenuti `RADAR_KEEP_S` (3 h). Se mancano numpy/Pillow fallisce solo questo job ("librerie mancanti" nel registro).
  - Le previsioni si salvano **intere** (`past_days=1`, da ieri alle 00); `api.trim_forecast()` le taglia **al momento della richiesta** a "da ieri alle 23:00" (giornalieri da oggi), con l'ensemble dalla stessa ora: così restano giuste anche dopo mezzanotte senza riscaricare.
  - `api/forecast` restituisce la stessa forma di prima (`schema` = `FORECAST_SCHEMA` di `config.py`, **uguale** a quello di `js/storage.js`; `fetchedAt` = download delle previsioni dalla fonte; `incomplete` se manca un ensemble recente o i metadati di un modello). L'ensemble si serve solo se ha meno di `ENSEMBLE_MAX_AGE_S` (12 h), con il suo `fetchedAt`; il frontend segnala nel dettaglio della probabilità un ensemble con più di 6 ore ("gli ultimi aggiornamenti non sono riusciti"). Il JSON composto è tenuto in memoria finché non cambiano i dati o il giorno.
- **Download nel frontend** (`load()` in `app.js`, `fetchForecast()` in `api.js`): l'app chiede i dati solo al proprio server.
  - Un solo download alla volta (`state.loading`); timeout di 20 s (`TIMEOUT_MS` in `api.js`); errori già in italiano (`ApiError`: rete assente, server che non risponde, messaggio `error` dell'API, es. "dati non ancora disponibili" con 503).
  - Ricontrollo del server ogni `CACHE_TTL_MS` (10 min) dall'ultimo controllo: `checkedAt`, aggiunto dall'app ai dati ricevuti (`nextDownloadAt()` / `isFresh()` in `storage.js`). Grazie all'ETag il browser riceve 304 e non riscarica il JSON se non è cambiato. Il timer al minuto in fondo ad `app.js` ricontrolla alla scadenza (oltre che al ritorno in primo piano/online).
  - La cache del localStorage si mostra solo se più recente di `state.data` (`fetchedAt`). Previsioni scaricate (dal server) da più di un giorno (`MAX_AGE_MS` / `isExpired()` in `storage.js`) non si tengono: `getCachedForecast()` le elimina dallo storage e `load()` le toglie anche dallo schermo (offline il timer al minuto richiama `load()` alla scadenza).
  - Forma dei dati salvati versionata con `FORECAST_SCHEMA` (`storage.js` e `server/config.py`): **incrementarla in entrambi se cambia l'oggetto di `api/forecast`**; le cache con schema diverso vengono scartate.

Su desktop il box ha 20 px di margine destro per il pallino. Nei giorni coperti solo in parte da un modello (fine orizzonte) si mostrano solo le fasce, senza riepilogo giornaliero.
- Alba e tramonto (`daily.sunrise` / `daily.sunset`, mostrati sotto il nome del giorno) sono dati astronomici identici per i due modelli: `api.js` li salva una sola volta, fuori da `daily.models`. Le cache senza questi campi vengono riscaricate. `.sun` (`sunTimes()`) è una riga flex: alba a sinistra, **tramonto allineato a destra** (`margin-left: auto`), pillole compatte ovunque. **Oggi** (`.sun.day24`, alta 46 px) al posto della riga c'è la **linea dell'intera giornata, da 00 a 24** (`.sun-track`): notte grigia (`--day-night`), giorno con la sfumatura alba → mezzogiorno → tramonto (`--day-dawn` / `--day-noon` / `--day-dusk`), spessa 3 px, opacità .45, senza tacche, con notte e giorno che si fondono in circa un'ora (4% della giornata) prima dell'alba e dopo il tramonto; le due pillole stanno **sotto**, centrate sul loro orario (`--at`, con `clamp()` per non uscire dai bordi), con in alto una **punta a fumetto** (`::before` con forma morbida, cima arrotondata e lati concavi, `clip-path: path()`, sovrapposta di 1 px al bordo della pillola per non lasciare fessure; colore `--pill-tip` = centro della sfumatura della pillola) rivolta al punto dell'alba / del tramonto sulla linea (la punta è al centro della pillola: alle nostre latitudini la pillola non arriva mai ai bordi, quindi coincide con l'orario). Le posizioni sono `--rise` / `--set` / `--noon` in % impostate da `sunTimes()`. Sulla linea all'ora attuale (`--now-f` = frazione delle 24 ore): icone da 20 px (traccia alta 20 px, linea al centro): di giorno il sole (`SUN_NOW`) colorato secondo il punto tra alba e tramonto (`--sun-c`, `sunColor()` interpola i token `--day-*` di `style.css`, formato `#rrggbb`, uguali nei due temi), di notte (`.night`) la **luna piena** (`MOON_NOW`, `.moon-now` con colori per tema); nel `title` il tempo mancante al tramonto / all'alba. `updateSunNow()` aggiorna dopo ogni `renderDaily()` e a ogni tick del timer al minuto, senza ridisegnare. Gli altri giorni: solo le due pillole, alba a sinistra e tramonto a destra. Nel layout largo la colonna del giorno ha poi l'etichetta di concordanza (`.day` area `"name models" "delta models" "bike bike"`: la concordanza sta sotto le info del giorno, i box dei modelli occupano entrambe le righe).  Icona condivisa: `sunEventIcon()` in `weather.js`; colori nei token `--dawn-*`, `--dusk-*`, `--sunset`.
- **Tragitti in bici** (righe sotto la concordanza in "Prossimi giorni"): elenco in `BIKE_COMMUTES` (`app.js`), ognuno con `label` e `windows` (ora locale). Attualmente:
  - un'unica voce, **configurabile nella pagina Impostazioni** (`settings.html`, sezione "Intervalli monitorati", salvata in `settings.watch`): nome (predefinito "Bike", max `MAX_WATCH_LABEL` caratteri, inserito con `esc()`) e da 1 a 6 intervalli (al massimo 3 per giorno), ognuno con i giorni della settimana in cui vale (predefiniti 06:45–08:00, 12:30–15:00, 17:00–18:30, tutti i giorni, `DEFAULT_WATCH` in `storage.js`). `renderBike()` mostra in ogni giorno solo gli intervalli di quel giorno della settimana (nessuno → niente riga); `--bike-max` (colonne su mobile) e la verifica di `fitBikes()` contano i blocchi della riga più lunga nel DOM. `BIKE_COMMUTES = [store.getWatch()]`; tornando dalle Impostazioni (`pageshow` da bfcache) o con modifiche da un'altra scheda (`storage`) `reloadSettings()` lo rilegge e ridisegna. Dati salvati non validi tornano ai predefiniti (`normalizeWatch()`). Il layout desktop prevede ancora un eventuale secondo tragitto nella colonna di ICON-EU.
  - Layout: tutti i blocchi (tutti i tragitti, tutti i giorni) hanno la stessa larghezza, quella del più largo (`fitBikes()` → `--bike-chip-w` su `#daily`, da richiamare dopo ogni render di "Prossimi giorni" e al resize; misura i blocchi con la classe `.bikes-measure`, cioè a `max-content`, altrimenti nella griglia stretta risulterebbero compressi). Su desktop i tragitti stanno **sulla stessa riga, allineati alle colonne del giorno** (`.bikes` grid: colonna `--label-w` + 15 px, poi due colonne uguali con spazio 1 px = box ICON-2I / ICON-EU): etichetta di Bike to work nella colonna dei nomi e blocchi sotto ICON-2I, Bike to school (etichetta + blocchi) dal bordo di ICON-EU. Se i blocchi non entrano nelle colonne, o con il giorno su una colonna (≤720 px), `fitBikes()` aggiunge `.bikes-flow`: tragitti uno dopo l'altro, a capo se serve. Su mobile (≤560 px) un tragitto per riga, etichetta sopra e blocchi a colonne uguali (`--bike-max`). Gli orari sono sempre in formato HH:MM–HH:MM.
  - Blocchi = `<button class="bike-chip" data-tip>`: icona di stato (`BIKE_STATUS`: sole = Asciutto, nuvola = Rischio, nuvola con goccia = Incerto, ombrello = Pioggia), al tocco il dettaglio (mm per modello, probabilità) va nello stesso avviso dell'etichetta di concordanza. Blocco compatto ovunque (desktop e mobile): orario sopra, icona + % sotto; testo dello stato, mm e "solo EU" nascosti (sono nel tooltip/avviso). Su desktop i blocchi hanno la larghezza del più largo (`fitBikes()`) e partono allineati ai box dei modelli; su mobile (≤560 px) ogni tragitto è una sola riga a colonne uguali (`--bike-max`).
  Per aggiungere un secondo tragitto servirebbe estendere `BIKE_COMMUTES`, `settings.watch` e la pagina Impostazioni.
  - Pioggia e probabilità orarie di Open-Meteo si riferiscono all'ora **precedente** il timestamp: `windowHours()` mappa la finestra sulle ore API con peso di sovrapposizione (es. 12:20–14 → 13:00 × 40/60 + 14:00).
  - Verdetto (`bikeVerdict()`): combina i modelli (quelli mostrati + i modelli di supporto ICON-D2 e AROME dove coprono il tragitto) con la probabilità dell'ensemble. Un modello "vede pioggia" se ≥ `BIKE_WET_MM` (0,2 mm) nel tragitto. **Pioggia** = maggioranza (più di metà: entrambi su 2, 2 su 3, 3 su 4) + prob ≥ 30% (`BIKE_POP_MOST`), oppure almeno uno + prob ≥ 60% (`BIKE_POP_ONE`), oppure prob ≥ 80% (`BIKE_POP_ANY`); **Asciutto** = nessuno + prob < 20% (`BIKE_POP_DRY`); **Rischio** = nessun modello ma prob ≥ 20%; **Incerto** = tutti gli altri casi. Senza probabilità si giudica solo sui modelli. Il motivo ("Perché: …") è nel dettaglio del blocco. mm mostrati: media se tutti i modelli vedono pioggia, altrimenti intervallo min–max. Niente media semplice dei mm per il verdetto: nasconderebbe il disaccordo. (Introdotto dopo il caso di venerdì 9/10: "Pioggia" al 38% e "Incerto" al 70% con la vecchia regola basata solo sui modelli.)
  - Se un modello non copre la finestra si usa l'altro ("solo EU"); finestre già trascorse di oggi attenuate.
  - **Probabilità nel tragitto** (`windowRainChance()`): per ogni ensemble (`data.ensemble.groups`) quota di scenari con almeno `ENSEMBLE_WET_MM` = `BIKE_WET_MM` (0,2 mm) **in almeno una singola ora** dell'intervallo (per le ore parziali la parte nell'intervallo, pesata): stessa soglia dei modelli (con 0,1 mm contavano anche poche gocce). Vale per tragitti e fasce. **Non** basta la somma delle ore: con dati arrotondati a 0,1 mm due ore da 0,1 mm facevano contare scenari quasi asciutti (caso del 9/10: fascia 12–18 al 45%, ~9 punti solo da scenari così, con le ore al massimo al 25%; con la regola attuale ~36%). mm "tipici"/massimi nel dettaglio = totale dell'intervallo degli scenari bagnati. I modelli invece "vedono pioggia" con la somma nel tragitto (≥ 0,2 mm). Il dettaglio riporta anche quanta pioggia danno gli scenari bagnati (mediana e massimo, `rainWords()`: qualche goccia < 0,5 · debole < 2 · moderata < 5 · forte) e, se nelle ore del tragitto un ensemble ha dati ogni 3 ore con pioggia (ECMWF ENS sempre, ICON-EU-EPS oltre ~48 h; `blockStart()`), la nota "Orario approssimato" con i nomi di quegli ensemble (`coarse` = elenco). **Non** usare la massima delle probabilità orarie: sottostima i tragitti su più ore, perché scenari diversi piovono in ore diverse (verificato: es. 45% vs 50% reale). Se l'ensemble manca si ripiega sulla massima oraria, mostrata con "~" e segnalata nel tooltip.
  - **Più ensemble**: la probabilità è la **media delle quote** degli ensemble che coprono l'intervallo con almeno metà dei loro scenari (ognuno pesa uguale, non ogni scenario: altrimenti i 51 di ECMWF ENS prevarrebbero sui 20 di ICON-D2-EPS). Il risultato ha `parts` (`{ model, wet, total }` per ensemble, mostrati da `chanceText()`); mediana e massimo dei mm sono sugli scenari bagnati di tutti gli ensemble. Oltre ~48 h restano ICON-EU-EPS ed ECMWF ENS.
  - Ensemble API: con **un solo modello** richiesto le chiavi non hanno suffisso (`precipitation`, `precipitation_member01`…); con più modelli sì (`…_icon_eu_eps`, `…_icon_d2_eps`). `fetchEnsemble()` chiede sempre più modelli e cerca il suffisso.
  - La `precipitation_probability` oraria di Open-Meteo è "quota di membri ICON-EPS/ICON-EU-EPS con > 0,1 mm/h" ma non è riproducibile esattamente dai membri dell'Ensemble API (scarto medio ~3 punti, run/elaborazione diversi): nella colonna del giorno resta quella dell'API. **Colonna "Prob." del dettaglio orario** (`popCell()`): stesso calcolo dei tragitti applicato alla singola ora (`windowRainChance([{stamp, weight: 1, i}])`: scenari degli ensemble con ≥ 0,2 mm nell'ora), dettaglio in tooltip / avviso al tocco (`chanceText()`, condiviso con i tragitti); "~" = stima Open-Meteo dove l'ensemble non arriva. L'ensemble è scaricato per 6 giorni (`fetchEnsemble()`). Lo stesso valore orario è disegnato nel **grafico "Precipitazioni"** come area azzurra con linea su una seconda scala a destra 0–100% (`VARIABLES.rain.pop`; in `chart.js` opzione `y2` e serie con `axis: 'y2'`, disegnate dietro barre e linee).
- **Concordanza dei modelli** (`agreement()` in `app.js`, soglie in `AGREE`): somma di punti di disaccordo, 0 → concordi, 1 → lievi differenze, ≥2 → discordi.
  - Temperature: differenza maggiore tra massime e minime ≥ 1,5° → 1 punto, ≥ 3° → 2.
  - Pioggia per fasce di 6 h (solo dove entrambi hanno dati): disaccordo se un modello ≥ 1 mm e l'altro < 0,3 mm (valori intermedi non giudicati); 1 fascia → 1 punto, ≥ 2 → 2.
  - Quantità (solo se piove per entrambi e le fasce concordano): uno ≥ doppio dell'altro e scarto ≥ 3 mm → 1 punto.
  - Temporale (codice WMO ≥ 95) in una fascia per un solo modello → 1 punto.
  - Raffiche: scarto ≥ 15 km/h con almeno uno ≥ 30 km/h → 1 punto.
  - Il motivo (criteri violati + aspetti concordi + differenze "Δ max · Δ pioggia (2I − EU)") va nel `title` dell'etichetta e, al clic/tocco, in un avviso (su touch il tooltip non esiste). Le differenze Δ non sono mostrate accanto all'etichetta (né su desktop né su mobile): sono solo nel tooltip/avviso.
  - Avviso (`toast()` / `hideToast()`): si chiude con un secondo tap sulla stessa etichetta, con un tap sull'avviso o in qualsiasi altro punto della pagina, oppure da solo dopo 9 s; un tap su un'altra etichetta lo sostituisce. `width: max-content` serve perché con `left: 50%` la larghezza disponibile sarebbe metà schermo.

## Chiavi localStorage

Prefisso `meteo:` — `settings` (con `radarOpen` / `riversOpen` = sezioni Radar / Fiumi aperte; `theme` = `auto` / `light` / `dark`, letto anche da `theme.js`; `models` = `both` / `i2i` / `eu`; `watch` = `{ label, windows: [{ from, to, days }] }` con `days` = giorni 0 (domenica) … 6 (sabato) come `parts().wd`; assente = predefinito; intervalli salvati senza `days` valgono tutti i giorni (`normalizeDays()`)), `station`, `fc:<lat>,<lon>` (lat/lon con 3 decimali, una sola voce: Faenza). All'avvio `removeLegacyKeys()` elimina `favorites`, `lastLocation`, `cacheIndex` e tutte le chiavi `fc:` di località diverse da Faenza, rimaste dalle versioni con località selezionabile.
Se cambia la forma dei dati salvati, gestire o scartare i dati vecchi in lettura (per le previsioni: `FORECAST_SCHEMA`).

## Convenzioni di sviluppo

- **`info.html` riporta soglie e regole in chiaro** (0,2 mm, 20/30/60/80%, ensemble usati e media tra ensemble, pioggia in corso e correzione della temperatura dalla centralina, 2 ore o 1 mm per le fasce, criteri di concordanza, orizzonti e frequenza dei modelli, frequenza dei download, letture della centralina): se cambiano nel codice (`NORMALS` e colori degli scarti nella sezione "Le medie del periodo" (`#medie`), `BIKE_*`, `SLOT_*` compresa `SLOT_RAIN_LEVELS` con la tabella delle icone "Le icone delle fasce" (`#icone`, icone disegnate con `icon()` da uno script nella pagina), `AGREE`, `ENSEMBLE_WET_MM`, `rainWords()`, `STATION_*`, `RAIN_NOW_*`, `TEMP_FIX_*`, `ENSEMBLE_MODELS` di `server/sources.py`, soglie del radar in `server/radar.py` (`RAIN_MMH`, `ARRIVE_FRAC`, `MAYBE_FRAC`, `radius_km()`, `NEAR_KM`, `LEADS`) e `RADAR_BIKE_MIN` / `radarWords()` di `js/radar.js` nella sezione `#radar`, frequenze del server in `deploy/crontab` / `server/config.py`, `CACHE_TTL_MS`), aggiornare anche la pagina.

- **Dopo ogni modifica a file della shell, incrementare `VERSION` in `sw.js`**, altrimenti gli utenti continuano a vedere la versione in cache. Se si aggiunge un file, inserirlo anche nell'array `SHELL`. Le richieste a `/api/` non devono mai passare dalla cache del service worker.
- **Server**: dopo una modifica a `server/` riavviare l'API (`systemctl restart meteo-api`); i job li rilegge cron a ogni esecuzione. Nuova fonte o nuovo dato: scaricarlo in un job e salvarlo nel database, mai dal browser; aggiungere un test in `tests/` se c'è logica di normalizzazione. **Limiti di Open-Meteo**: l'archivio (30 anni) vale molte chiamate e con prove ripetute risponde 429 per un po'; nei test usare dati già salvati (`METEO_DB` su un file di prova).
- Prima di inserire testo proveniente da API nell'HTML usare `esc()` (`weather.js`).
- Layout mobile-first: verificare a 390 px di larghezza che non ci sia scroll orizzontale della pagina, e su desktop a 1200 / 1400 / 1920 px (colonna sinistra 288–468 px).
- Le sezioni "Adesso" e "Prossimi giorni" condividono la stessa griglia (`.day` → `.day-name` + `.day-models` a due colonne, larghezza etichetta `--label-w`): le colonne ICON-2I / ICON-EU devono restare allineate verticalmente a ogni larghezza. Non dare a una sola delle due sezioni padding o colonne diverse.
- Grafico "Andamento orario": parte dall'ora piena **precedente** a quella attuale (alle 20:32 inizia alle 19, `nowIndex() - 1`); i tab seguono l'ordine di `VARIABLES`, con **Precipitazioni per prima** (anche variabile predefinita).
- Nuove variabili del grafico: aggiungerle a `VARIABLES` in `app.js` (e a `HOURLY_VARS` in `api.js` se non già scaricate).
- Rigenerare le icone PNG (Pillow) se cambia `icons/icon.svg`: 192, 512, maskable 512 (senza angoli arrotondati), apple-touch 180.
